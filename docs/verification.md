# 验证与发布

## 自动检查

使用仓库指定的 Node.js 和 npm，安装依赖后执行：

```sh
npm run check
```

| 命令 | 检查内容 |
| --- | --- |
| `npm run lint` | 代码规范。 |
| `npm run typecheck` | 生成 Next.js 路由类型并检查 TypeScript。 |
| `npm test` | 内容、元数据、图片、导出及独立交互逻辑的回归检查。 |
| `npm run check:fonts` | 使用 Python 3 标准库检查字形覆盖与生成物完整性。 |
| `npm run build` | 生产构建。 |
| `npm run verify:site` | 为当前构建启动临时本地服务，执行完整抓取检查，并在成功或失败后关闭服务。 |

`check` 依次执行以上步骤，GitHub Actions 使用同一入口。`verify:site` 不重新构建：代码变化后应先构建或直接运行 `check`，避免验证旧页面。它不占用已有的评审服务。

字体缺少新字符时按 [字体维护](site-fonts.md) 重新生成，不要绕过检查。某次通过的测试数量和页面数量只适用于当次版本，不作为长期维护指标写死。

## 指定网站的抓取检查

对已经运行的预览或正式站执行只读检查：

```sh
npm run audit:seo -- http://127.0.0.1:3101
npm run audit:seo -- https://www.darren-su.com
```

该检查从 sitemap 遍历页面，核对 HTTP 状态、可直接读取的正文、标题、规范地址、语言版本、结构化数据、内部链接、文章图片、Markdown 来源、RSS 和抓取入口。会实际请求图片响应，不以磁盘文件存在替代检查。它不向搜索平台提交收录，不验证站外引用的每个事实，也不能证明真实爬虫已访问。

需要长时间人工查看生产构建时，可自行启动：

```sh
npm run build
npm run start -- --hostname 127.0.0.1 --port 3101
```

生产预览不会自动反映源码变化，修改后需要重新构建、停止旧服务并重新启动。日常修改优先使用 `npm run dev`。

## 浏览器走查

界面或交互改动后，在桌面和手机宽度下检查受影响路径，并保留中英文及日光 / 暮色的代表样本：

- 从首页房间热点与普通导航进入案例、产品、文章、关于和合作，确认入口含义与目标一致。
- 进入案例与文章详情，检查封面、正文图片、目录、代码块与长英文的排版；手机页面无整体横向溢出，代码块可独立横向滚动。
- 切换语言后仍到达对应内容；阅读章节定位、暮色参数与导航状态合理保留。
- 打开手机菜单、产品详情与联系入口，确认能读清内容、返回或关闭。检查邮箱和预填主题，不为验证而发送消息。
- 拖动 3D、使用等价键盘按钮、切换静态浏览，检查失败回退及减少动态偏好；普通内容和链接应始终可用。
- 对导航或客户端边界的变更，补查禁用 JavaScript 时的正文、导航、语言和联系链接。

浏览器模拟手机宽度不能代替真实 iOS / Android 的性能、耗电和 Safari 兼容性。需要性能测量时记录版本、设备、网络、缓存和测量方式；不要把本地 Lighthouse 结果当作线上用户体验或 INP 分布。

## 发布与回退

1. 在独立分支完成改动，运行 `npm run check` 并走查受影响界面。
2. 检查待提交文件，只包含公开内容、实现与必要维护资料。保留原图许可、署名和资料来源；密钥与未采用的私人稿件不入库。
3. 经用户授权后发布到 `main`。现有 Vercel Git 集成会触发正式部署；确认部署成功且对应预期提交。
4. 在正式域名运行抓取检查，并复查首页、文章、语言切换和联系入口。部署成功不等于页面内容已核验。

出现问题时保留故障证据与对应提交，按影响选择修复后重发或回退上一已验证版本。不要用强制覆盖分支的方式丢弃其他改动。

实际索引、搜索词及引用表现需要从 Google Search Console、Bing Webmaster Tools 等授权后台查看。没有读取后台时，应明确写“未核验收录”，而不是把抓取成功写成已经收录。
