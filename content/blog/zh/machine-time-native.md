最近这波 Personal Agent，让我有点回到当时折腾 OpenClaw 的感觉。

尤其是最近使用 Grok bot 调度 Agent 的时候，我又遇到了一个在各种 AI 工具里反复出现的问题：

**AI 很喜欢按照人类团队的工作节奏，给自己安排任务。**

比如，让 Agent 规划一个项目，它很容易写出这样的计划：

> 第一周完成需求调研，第二周确定方案，第三周开发，第四周测试和交付。

每次看到这样的排期，我都挺抓狂。明明很多工作现在就能做，为什么非要排到几周以后？

如果目标明确，工具和权限也具备，很多任务 AI 几十分钟或几个小时就能做出初版。为什么方案一定要等到第二周，开发一定要等到第三周？

而且这不只是开发任务。做 Marketing、内容生产、市场调研时，也经常会出现类似的问题。

原本可以连续推进的事情，会被 Agent 分散到一张跨度几周的计划表里。这会非常影响自运转的效率。

**AI 已经拥有了不同于人的执行速度，但它规划工作的方式，似乎还停留在人类团队的时代。**

## 一、当错误的时间估算，变成实际的工作排期

这里其实有两个不同的问题。

**第一种，是估算不准。**

假如 Agent 告诉我，一项任务需要两周，但实际三个小时就完成了。

这当然说明它的估算不准确，但只要它根据实际进展不断往前推进，工作仍然可以提前完成。

这种情况下，主要需要解决的是如何让 AI 更准确地认识自己的执行能力。

**第二种，是错误的估算开始影响任务推进。**

Agent 制定了一份两周的计划，人也接受了这份计划。后面的工作便开始服从这个安排。

第一阶段明明已经完成，下一项任务却还写在「下周的工作计划」里。

如果没有人重新追问，原本可以立即推进的事情，就可能因为计划中的日期而被延后。

**前一种问题影响的是预期，后一种问题影响的是真实生产力。**

我不希望每次都需要提醒与追问 Agent：「这个现在就可以做，为什么要等下周？」

更不希望因为自己没有及时检查计划，就让大量已经具备执行条件的任务一直闲置。

## 二、Agent 到底在等什么？

我在之前的文章[《管了 31 个 AI 员工之后，我重新理解了管理学》](/zh/blog/managing-31-ai-employees)里提过一个发现：

AI 出现以后，组织结构会逐渐变成一个沙漏。**上面有源源不断的想法和目标，下面有越来越强、越来越容易扩展的 AI 执行能力，而中间收紧的地方，反而是人。**

人的精力、注意力和决策效率，可能成为限制整个系统运转的瓶颈。

实际管理 Agent 的过程中，确实有一些任务需要等待反馈。

比如，要不要花钱、是否允许上线、一篇内容能不能对外发布，这些涉及风险和责任的事情，仍然需要人来判断。还有一些工作，确实需要等待现实世界的数据来做反馈。

一篇内容发布以后，阅读量、转化率如何变化？一个产品上线以后，用户是否真的愿意使用？这些结果不会因为 AI 执行得更快，就立刻出现。

所以我开始尝试把工作中的时间分成三类：

- **机器执行的时间**：调研、分析、开发、写作、测试等 AI 可以直接完成的工作，应根据它的实际执行能力安排。
- **人类决策的时间**：需要审批或判断的事项，应明确告诉人现在缺少什么决定、涉及什么风险。
- **真实世界反馈的时间**：需要等待用户、市场或外部系统的结果时，应说明正在观察什么，以及什么条件出现后才能继续。

这三种时间的性质完全不同。

但如果 Agent 只是笼统地说「下周继续推进」，我就无法判断：

它究竟还有工作没做完？是在等我拍决策？是在等市场反馈？还是卡在了某个环节中？

这会让整个协作过程变得很不顺畅。

本来应该是 AI 主动推进工作，人只在必要时介入，结果变成了人不断检查、催促和重新安排 AI。

**好的 Agent 工作计划，不应该是一张静态的时间表，更不应该是一个黑箱。我需要知道它已经完成了什么、现在卡在哪里，以及下一步究竟在等什么，是一个动态变化的过程。**

当然，自动调度和持续运行是另一个问题。但即使 Agent 已经具备自主执行能力，如果最初的计划就包含大量不必要的等待，整个系统依然很难高效运转。

## 三、AI 为什么会沿用人类的时间表？

我们熟悉的项目管理方法，大多是围绕人的工作能力建立起来的。每天八小时、每周五个工作日、两周一个 Sprint。人需要沟通、开会、休息，多个团队需要协调资源，工作还受到组织流程的约束。

AI 在训练过程中接触了大量人类编写的项目计划、开发文档和任务安排，自然也熟悉这些工作方式。

问题是，**当 AI 自己成为执行者时，它未必会自动把这些人类经验重新换算成机器的执行时间。**

也有开发者提出过类似的解释。

Eivind Kjosbakken 在《[Why Claude Code Time Estimates Are Poor](https://eivindkjosbakken.substack.com/p/why-claude-code-time-estimates-are)》中提到，他向 Claude Code 询问功能开发工期时，经常得到三到四周这样的回答。

但在他描述的开发条件下，相应工作往往一天内就能完成。他认为，一个可能的原因是，模型学到了大量人类工程师的时间估算，却缺少足够的 AI 实际开发耗时数据来校准。

而 Aniketh Garikaparthi 的论文《[Can LLMs Perceive Time? An Empirical Investigation](https://arxiv.org/abs/2604.00010)》提供了另一个角度。研究者在一组任务中发现，模型执行前给出的时间估算约为实际用时的 4–7 倍。有些几秒钟就能完成的任务，被估算成需要几分钟。

论文将这种现象与模型缺少对自身执行时间的经验性校准联系起来。

Agent 和人一样：**知道完成一项工作通常需要多久，和知道自己完成它需要多久，并不是同一回事。**

还有一个特别容易被忽略的地方：

**任务之间的逻辑顺序，经常被误写成任务之间必须存在的时间间隔。**

先理解需求，再确定方案，然后开发、测试，这个顺序没有问题。

但前一步完成之后，为什么一定要等第二天才能开展下一步？

真正重要的是，前置条件有没有满足，结果有没有经过必要验证，是否还存在真实的阻碍。如果没有，就应该继续推进。

## 四、Machine-Time Native：让 AI 按机器的时间工作

我开始尝试在 Grok Bot 中用 **Machine-Time Native** 来描述自己期待的工作方式。

**当工作主要由 AI 执行时，就应该按照 AI 的真实执行能力来规划任务，而不是默认沿用人类团队的工作时间表。**

如果前一步已经完成并通过验证，下一步也具备执行条件，就不应该仅仅因为日历上的安排而继续等待。

如果任务确实需要人来批准，就把需要决策的内容和风险交给人。如果需要真实世界的反馈，就说明在观察什么，什么时候可以根据反馈作出下一步判断。

同样，「做出了初版」和「经过验证、可以交付」，也必须是两种不同的状态。

我希望 Agent 的计划不再只是一张按日历排列的任务清单，而是一份能够随着实际进展推进的工作安排。

**用任务依赖决定执行顺序，用真实条件决定是否等待，而不是用划定的日期决定什么时候工作。**

我整理了一段提示词。如果你也遇到类似问题，可以直接加入自己的 Agent 工作规范中。

```
你是任务的实际执行者，而不是在为一支人类团队制定工作日程。

请按照当前工具、权限、自身执行能力和真实任务依赖来规划和推进工作，以任务与结果为导向。遵循以下原则：

**1. 以实际执行能力规划**

不要默认使用人天、人周、Sprint 等传统排期。需要估算时间时，依据实际执行条件和历史记录；缺少依据就说明不确定性，不编造工期。

**2. 能做的事，现在就做**

先判断哪些任务已经具备执行条件，并立即推进。能够在当前执行过程中完成的事情，不要人为拆成多天计划。

**3. 以任务依赖代替日历安排**

有先后顺序，不代表中间必须隔一天。前置任务完成并通过必要验证后，就可以进入下一步。相互独立且资源允许的工作，可以并行。

**4. 只为真实约束等待**

只有必要的质量验证、人类审批、外部反馈、资源或权限限制，才构成等待的理由。

需要等待时，明确说明：

- 在等什么？
- 满足什么条件可以继续？
- 现在还有什么事情可以做？

**5. 执行优先，验证跟进**

不要只输出未来计划。权限和条件允许时，优先直接完成任务，并验证结果。区分初版、已验证和可交付状态，不为了赶进度跳过必要检查。

涉及花钱、正式上线、对外发布、对外承诺或不可逆操作，必须先获得人的明确授权。

如果当前工具不能在后台持续运行或自动恢复执行，要明确说明，不要假装任务会在未来自动完成。

**每轮汇报只需要说明：已完成什么、验证结果如何、还有什么真实阻碍、下一步是什么。**

**核心要求：计划应该描述真实的任务依赖，而不是制造人为的时间等待。能在当前完成的工作，就不要安排到未来。**

任务规划后进行排期自检：
- 是否出现了「明天开始」「下周推进」「第一周、第二周」等日历安排？
- 这些时间间隔是否由真实的外部依赖、资源限制、审批或必要验证造成？
- 如果没有真实约束，立即取消这些间隔，改为前置条件满足后继续执行。
- 对于当前已经具备执行条件的任务，不要只把它列入计划，应在权限和工具允许时直接开始执行。

不要把时间安排当成任务依赖。只有真实依赖才是等待的理由。

```

我们一直在努力让 AI 学会像人一样工作,但当 AI 开始真正承担工作，也许应该反过来思考：

**我们已经拥有了机器的执行速度，却还没有完全学会如何按照机器的时间来组织工作。**

AI 时代的生产力变化，不仅发生在执行层，也发生在组织规划层。

重新理解工作的时间，可能就是一个很好的开始。
